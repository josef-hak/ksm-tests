**What this PR does / why we need it**:

Adds `403_mcsdep_diamond`: four MultiClusterServices in a dependency graph that is not a chain — `certs` is depended on by `crds` and `proxy`, and `workload` depends on both.

[`401_mcsdep_valid`](test_scenarios/401_mcsdep_valid.md) proves one `dependsOn` edge is honoured. A single edge cannot show that an MCS waits for *every* dependency rather than for whichever reports in first, and it cannot show a dependency being awaited by two MCSs at once. This is the smallest shape that covers both directions.

The gap is not hypothetical. The KCM e2e suite has a `mothership` leg with exactly these two topologies (`mcs3->(mcs1,mcs2)` and `(mcs1,mcs2)->mcs3`), it runs only when a maintainer names it in an approval comment, and k0rdent/kcm#3186 is removing it as duplicated by this repository. It is duplicated apart from the graph shape, which is what this scenario takes over.

**Choices worth flagging**

- *The services are the kserve stack split across the graph, not four arbitrary charts.* `kserve-resources` renders a Certificate and a `ClusterStorageContainer`, so installing it before `cert-manager` and the kserve CRDs are really there fails the helm release outright. A leaking gate is then a hard failure, not only a lost timing comparison.
- *`proxy` carries traefik, which needs nothing from `cert-manager`.* It is the half of the fan-out held back by the MCS edge alone — if the gate were keyed on services rather than on the MCS, this is the one that would start early.
- *Declaration order is teardown order reversed.* `remove_services.sh` deletes from the last declared backwards, so `workload` (kserve-resources) goes before `crds` (kserve-crd). The other order is the teardown failure documented in [`201_svcdep.yaml`](test_scenarios/201_svcdep.yaml).
- *No runner changes.* `dependsOn` was already a list and `deploy_mcs_group.sh` checks each key against all of its dependencies, so this is a scenario file and the wiring the consistency tests require.

**What this does not cover**

Two assertions from the KCM leg have no home here yet, and both need runner work rather than YAML: deletion of an MCS being refused while another depends on it (`remove_services.sh` deletes in dependency-safe order, so it never meets the refusal), and a dependent created before its dependency exists at all (everything is created in one apply, on purpose). Those are controller conditions rather than rollout behaviour, so the suggestion on k0rdent/kcm#3186 is to cover them in envtest there.

**Verification**

`scripts/tests/bash/run.sh` passes 11/11 — `test_services.sh` carries a hardcoded scenario list that needed the new id. Rendering was checked locally: four manifests, `workload` with both `dependsOn` entries. The scenario has not yet been run against a cluster.
